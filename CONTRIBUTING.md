# Contributing to guile-dokgen

guile-dokgen reads Guile modules and writes their API documentation as
Texinfo.  It is Guile source and a POSIX shell launcher under the MIT license,
and it has no build step.

## Try it, then run the suite

```shell
git clone https://github.com/jjba23/guile-dokgen.git
cd guile-dokgen
maak test        # runs inside a pinned Guix; it should be green before you change anything
```

`maak` runs every task through `guix time-machine -C channels.scm -- shell -m
manifest.scm`, so you need Guix and [Maak](https://codeberg.org/jjba23/maak),
and nothing else.

## Where things are

| Path | What it holds |
|---|---|
| `src/dokgen/data.scm` | extracting the API data from a module |
| `src/dokgen/diagrams.scm` | the mermaid and gnuplot diagrams a docstring carries |
| `src/dokgen/templates/stexi.scm` | rendering that data as stexi |
| `src/dokgen/writer.scm` | writing the result to disk |
| `src/dokgen/cli.scm`, `commands.scm` | arguments and dispatch |
| `test/veritas/unit/` | one spec per module, run by the veritas runner |
| `test/` | the fixture libraries and renderers the specs point at |
| `manual/` | the Texinfo manual (`api/` is generated by `maak docs`) |

## Making a change

1. Write the test first and watch it fail
   (`test/veritas/unit/<module>-spec.scm`).
2. Make it pass with the smallest change.
3. Update the manual and `CHANGELOG.org` when the change is visible to users.
4. Run `maak version-check check test docs-check`.
5. Commit as `type(scope): summary`, lower case, imperative.

The suite is written with [veritas](https://github.com/jjba23/veritas) and
run by `maak test`, which calls the runner over `test/veritas/unit`.  A spec is
a module named `(veritas unit <module>-spec)` that exports `spec`; it builds
suites and returns them from `(veritas-run ...)`.  The runner discovers the
files itself, so a new spec is a new file and nothing else:

```scheme
(define-module (veritas unit data-spec)
  #:use-module (dokgen data)
  #:use-module (veritas all))

(define (spec)
  (veritas-run
   (suite "A file path, as a module name"
          (test "a library with more than one module"
                (assert-equal #:expect '(libx module-a)
                              #:got (file-path->module-name
                                     "/home/user/x/libx/module-a.scm"
                                     "/home/user/x"))))))
```

A fixture is a library rather than a mock: the specs point `dokgen` at the
modules under `test/`, and a renderer is a shell script there, so the command
a project would pass is the command the suite runs.  Suites shuffle and run
their tests concurrently by default; give a test its own destination under
`/tmp` rather than relying on the order the cases run in.

Docstrings are Texinfo, because the tool renders them as such.  The first line
is a summary that stands alone; each argument follows as
`@strong{name} (type):` and the result as `@strong{Return value} (type):`.  A
module's description is its `;;; Commentary:` or a `#| ... |#` block, and every
exported name has one.  Run `maak docs` to see how they render.

A docstring may carry a mermaid or gnuplot diagram as a fenced block; the
manual's *Diagrams* chapter says how each is drawn.  The HTML does not need a
renderer: a mermaid diagram with no image is drawn in the page from the
bundled `mermaid.min.js`, and a gnuplot diagram is drawn at build time when
`gnuplot` is installed.  This project still commits its images so that Info
and print output have them.  `maak docs` writes each diagram's `.mmd` or `.gp`
next to the reference and points at the image beside it, so a diagram that
changed without its image following is a stale reference that
`maak docs-check` reports.  Draw one with

```shell
npx --yes @mermaid-js/mermaid-cli@11 \
    --input manual/api/diagrams/NAME.mmd --output manual/api/diagrams/NAME.png
gnuplot -e 'set terminal svg; set output "manual/api/diagrams/NAME.svg"' \
    manual/api/diagrams/NAME.gp
```

and commit both files.

Every source file starts with the header:

```scheme
;; guile-dokgen --- what this file is
;;
;; SPDX-License-Identifier: MIT

```

`AGENTS.md` is generated by `maak agents` from the practices in `maak.scm`;
edit the task, never the file.  The practices there (documentation, security,
SemVer, conventional commits, functional style) apply to people as well.
